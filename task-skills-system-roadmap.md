# Роадмап развития скиллов КАК СИСТЕМЫ

**Дата:** 2026-05-31
**Контекст продукта (пример):** платформа оценки рисков (risk assessment).
**Важно:** это роадмап эволюции системы скиллов. Сами скиллы по нему пока **не создаются**.

Этот документ смотрит на 4 скилла + интеграции **как на единый продукт** (систему «continuous architecture»), а не на отдельные скиллы. Ось «откуда берётся вход» вынесена в [task-skills-roadmap.md](task-skills-roadmap.md); здесь — ось **зрелости системы**: релизы, вехи, рост возможностей, метрики, риски.

---

## Видение системы

> **Единая система, которая держит продукт связанным: от стратегии (Vision) до ИТ-реализации — с автоматической трассируемостью, проверкой качества и обратной связью, работающая непрерывно.**

Системные принципы:
- Единый handoff-контракт (`id`/`trace_up`/`covers`) — основа всего.
- Gate-валидатор не пропускает несвязные артефакты.
- Human-in-the-loop на критичных переходах.
- Каждый релиз самодостаточен и приносит ценность.

---

## Модель зрелости системы

```
L0  Спецификация      → есть ТЗ скиллов, системы ещё нет
L1  Работающий каркас → скиллы запускаются вручную, цепочка связна
L2  Оркестрованная    → один запуск гонит всю цепочку + gate
L3  Подключённая      → вход из систем и переписки (MCP)
L4  Замкнутая         → петля доработки продукта (drift, инциденты)
L5  Автономная        → continuous-architecture по расписанию
```

Уровни L0→L5 соответствуют горизонтам данных Г0→Г5 из роадмапа источников, но измеряют **зрелость системы**, а не автономность данных.

## Релизный план

### R0 — Foundation (L0→L1)
**Цель:** превратить ТЗ в работающий каркас.
- Реализованы 4 скилла по ТЗ (`product-vision`, `business-architecture`, `it-architecture`, `architecture-validator`).
- Работает handoff-контракт и матрица трассируемости.
- Прогон вручную, скилл за скиллом.

**Exit-критерий:** сквозной прогон на «оценке рисков» проходит gate-валидатор.
**KPI:** 100% элементов имеют `id`+`trace_up`; gate выдаёт вердикт.

### R1 — Orchestration (L1→L2)
**Цель:** убрать ручную передачу между скиллами.
- Скилл `orchestrator` (запуск цепочки end-to-end).
- Скилл `constitution` (инварианты над Vision).
- Версионирование артефактов + changelog.

**Exit-критерий:** одна команда → валидированный пакет всех артефактов.
**KPI:** время полного прогона; доля ручных шагов → 0.

### R2 — Connected Inputs (L2→L3, MCP-источники)
**Цель:** вход формируется из реальных систем.
- Коннекторы к Drive/Notion, Linear/Asana, Airtable/DWH, репозиториям/CMDB.
- Автосверка as-is (из систем) vs to-be (артефакты).
- `provenance` (`source`) у каждого элемента.

**Exit-критерий:** ≥50% входа собирается без копипаста.
**KPI:** % авто-собранного входа; число найденных рассинхронов as-is/to-be.

### R3 — Conversational Inputs (L3, переписка)
**Цель:** извлекать намерения из переписки и встреч.
- Коннекторы Gmail/Slack/Teams, транскрипты встреч.
- Извлечение черновиков требований/ADR (`draft` + human approve).

**Exit-критерий:** система стабильно предлагает валидные черновики из переписки.
**KPI:** % принятых черновиков; lead time «обсуждение → артефакт».

### R4 — Closed Loop (L4, доработка продукта)
**Цель:** система дорабатывает живой продукт, а не только проектирует.
- Drift-детект (артефакты vs телеметрия/инциденты).
- Обратные триггеры (инцидент / фидбэк / регулятор) → delta-предложения.
- Подтверждённая delta → задача в трекере.

**Exit-критерий:** изменение в проде автоматически → трассируемое предложение правки.
**KPI:** доля изменений с трассировкой к Vision; время реакции на drift.

### R5 — Autonomous (L5, continuous-architecture)
**Цель:** система живёт сама, человек — на approve и эскалациях.
- Оркестратор по расписанию переснимает as-is, гонит цепочку, публикует diff.
- Авто-эскалация только при `principle-violation` / gate `fail`.

**Exit-критерий:** актуальность артефактов поддерживается без ручного запуска.
**KPI:** % времени «зелёного» gate; число эскалаций/период.

## Зависимости между релизами

```
R0 ─▶ R1 ─▶ R2 ─┬▶ R3 ─▶ R4 ─▶ R5
                └▶ (R3 и R4 могут идти частично параллельно
                     после готовности R2-коннекторов)
```

- R1 требует стабильного handoff-контракта из R0.
- R2 требует оркестратора из R1 (иначе источники некуда подавать централизованно).
- R4 требует provenance из R2 (drift нужно к чему-то привязывать).

---

## Системные риски и митигировка

| Риск | Релиз | Митигировка |
|------|-------|-------------|
| Контракт меняется → ломает связки | R0–R1 | версионирование + обратная совместимость схемы |
| Шум из переписки → мусорные требования | R3 | только `draft` + обязательный human approve |
| Утечка PII из источников/переписки | R2–R3 | маскирование, политика доступа, provenance-аудит |
| Автономность принимает плохие решения | R5 | gate-блокировка + авто-эскалация на принципах |
| Drift-ложные срабатывания | R4 | пороги, группировка, подтверждение человеком |
