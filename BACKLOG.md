# Бэклог доработок фреймворка

Список улучшений, выявленных при ревью SDD-цепочки
(`product-vision → business-architecture → it-architecture → validator`).
Сгруппирован по приоритету. Каждый пункт: что · зачем · где · фикс.

---

## P0 — дешёвые фиксы с высоким эффектом

### 1. Контракт-баг: `A-*` vs `ASSUMP-*`
- **Что:** `product-vision` эмитит допущения как `A-*`, а `business-architecture` /
  `it-architecture` и валидатор оперируют `ASSUMP-*`.
- **Зачем:** open-blocker-правило валидатора матчит `Q-*`/`ASSUMP-*` →
  допущение уровня vision с `severity: blocker` **невидимо для gate**.
- **Где:** [product-vision/SKILL.md:200](.claude/skills/product-vision/SKILL.md:200),
  [task-skill-4:53](task-skill-4-architecture-validator.md:53).
- **Фикс:** привести vision к `ASSUMP-*` **или** расширить паттерн валидатора до `A-*|ASSUMP-*`.

### 2. Детерминированный вердикт gate
- **Что:** нет таблицы «тип gap → severity → вердикт». `PASS/WARN/FAIL` назначается на глаз.
- **Зачем:** два прогона могут разойтись в вердикте (в few-shot `uncovered-capability`
  идёт как WARN, хотя это скорее блокер). Недетерминированный gate — это не gate.
- **Где:** [task-skill-4:37,57-70,140](task-skill-4-architecture-validator.md:57).
- **Фикс:** добавить таблицу маппинга каждого gap-типа в blocker/warning и порог вердикта.

## P1 — структурные дыры трассируемости

### 3. Версионный дрейф (`trace_up` без версии)
- **Что:** `trace_up` ссылается на `id`, а не на `id@version`.
- **Зачем:** бизнес-арх, построенная на vision `v0.1`, остаётся «валидной» после ухода
  vision в `v0.3` — связь формально цела, по смыслу мертва.
- **Где:** контракт во всех трёх скиллах; [task-skill-4:172](task-skill-4-architecture-validator.md:172).
- **Фикс:** хранить версию в `trace_up` и проверять, что родитель текущей версии.

### 4. Персист спеки в файл
- **Что:** скиллы пишут артефакт в markdown, но не сохраняют его в фиксированный путь.
- **Зачем:** без файла-источника истины нечему иметь стабильную версию (см. №3),
  валидатору нечего сверять «вхолодную» между сессиями, код не на что сослаться (см. №5).
- **Где:** [business-architecture/SKILL.md:53](.claude/skills/business-architecture/SKILL.md:53) (нет пути).
- **Фикс:** конвенция `specs/vision.md` / `specs/business.md` / `specs/it.md` +
  правило «обновляй файл, не плоди дубль».

### 5. Мост plan → код (`ADR-*` ↔ commit)
- **Что:** `covers` доходит только до компонента; трассировка рвётся на границе с кодом.
- **Зачем:** код может разойтись с ADR, и валидатор этого не увидит — самый дорогой стык.
- **Где:** нижний gate делегирован наружу [task-skill-4:19](task-skill-4-architecture-validator.md:19).
- **Фикс:** конвенция «коммит/PR несёт `trace_up: ADR-*`/`REQ-*`»; стык с
  разработкой/superpowers как нижний gate (`tasks ↔ implement`).

### 6. Покрытие North Star (`MET-*`)
- **Что:** правило покрытия — «GOAL/PRIN отражена в ≥1 CAP/REQ»; `MET-*` не входит.
- **Зачем:** North Star метрика без двигающей её capability проходит молча.
  Плюс «≥1» не проверяет достаточность.
- **Где:** [task-skill-4:45](task-skill-4-architecture-validator.md:45).
- **Фикс:** требовать, чтобы хотя бы одна `CAP`/`REQ` была привязана к каждой `MET-*`.

### 7. Feedback-блокеры валят gate
- **Что:** open-blocker-правило смотрит только `Q-*`/`ASSUMP-*`; `FB-*` с
  `severity: blocker` в статусе `open` gate не останавливает.
- **Зачем:** критичная обратная связь («нарушает PRIN-01») может зависнуть незамеченной;
  enablement проверяется только на наличие блока, не на разрешённость.
- **Где:** [task-skill-4:52-53](task-skill-4-architecture-validator.md:52).
- **Фикс:** включить `FB-*` со `severity: blocker` + `status: open` в open-blocker-проверку.

## P2 — режимы и семантика

### 8. Explore-режим валидатора (R&D)
- **Что:** валидатор одинаково жёсткий для исследовательских и разработческих артефактов.
- **Зачем:** жёсткий `FAIL` на непокрытую гипотезу душит R&D.
- **Фикс:** переключатель строгости по `status`:
  `draft` → WARN (не FAIL на непокрытие), `approved` → жёсткий gate.
  Доп. правило: каждая `draft`-цель обязана иметь хотя бы один `ASSUMP-*`/`Q-*`.

### 9. Триггер «когда ADR обязателен»
- **Что:** DoD требует «≥1 ADR», но не определяет, что считать ключевым решением.
- **Фикс:** ADR обязателен, если решение (а) трогает `PRIN-*`,
  (б) необратимо/дорого откатить, (в) породило `FB-*` наверх.

### 10. Семантическая трассировка (исследовательский пункт)
- **Что:** валидатор проверяет связи структурно (референциальная целостность),
  а «привязано формально, но не туда» не ловит.
- **Зачем:** это главная заявленная ценность фреймворка; сейчас она не гарантирована правилами.
- **Где:** [task-skill-4:43-53](task-skill-4-architecture-validator.md:43).
- **Фикс:** добавить семантическую проверку соответствия (LLM-судья) поверх структурной —
  отдельный режим, т.к. недетерминированный.
