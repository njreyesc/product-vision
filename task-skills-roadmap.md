# Роадмап развития скиллов: `Vision → Бизнес-арх → ИТ-арх → Validator`

**Дата:** 2026-05-31
**Контекст продукта (пример):** платформа оценки рисков (risk assessment).
**Важно:** это ТЗ-роадмап. Сами скиллы и интеграции по нему пока **не создаются**.

Документ описывает, как набор скиллов эволюционирует от «ручного ввода» к подключённым источникам, переписке и замкнутой петле доработки продукта.

---

## Принцип развития

Скиллы проходят путь по уровню автономности входных данных и обратной связи:

```
ручной ввод → подключённые источники (MCP) → переписка/неструктур. данные
            → замкнутая петля доработки продукта → автономная оркестрация
```

На каждом горизонте handoff-контракт (`id`/`trace_up`/`covers`) сохраняется — меняется только то, **откуда берётся вход** и **куда уходит выход**.

---

## Горизонт 0 — Базис (текущее ТЗ)

**Цель:** скиллы работают, цепочка связна.

- 4 скилла: `product-vision`, `business-architecture`, `it-architecture`, `architecture-validator`.
- Вход — вручную (текст, документы).
- Выход — структурированные артефакты + матрица трассируемости.

**Готово, когда:** сквозной прогон на «оценке рисков» проходит gate-валидатор.

---

## Горизонт 1 — Шаблоны, оркестрация, constitution

**Цель:** снизить ручной труд и закрепить инварианты.

- **Новый скилл `constitution`** — незыблемые принципы (архитектурные стандарты, регуляторные «нельзя», tech-radar) над Vision.
- **Новый скилл `orchestrator`** — запускает цепочку end-to-end, собирает финальный пакет, прогоняет валидатор.
- Версионирование артефактов + changelog.

**Готово, когда:** одна команда запускает всю цепочку и получает валидированный пакет.

---

## Горизонт 2 — Подключение источников через MCP

**Цель:** вход формируется автоматически из реальных систем, а не вручную.

| Источник (MCP) | Что подтягивает | В какой скилл |
|----------------|------------------|----------------|
| Notion / Google Drive / Confluence | стратегия, продуктовые доки, регуляторные требования | `product-vision` |
| Jira / Linear | бэклог, эпики, текущие capabilities as-is | `business-architecture` |
| Airtable / БД / DWH | данные о процессах, метрики, портфель | `business-architecture` |
| Репозитории кода / IT CMDB | ИТ-ландшафт as-is, тех-долг | `it-architecture` |
| BI / телеметрия | фактические KPI vs целевые | `validator` |

- Скиллы умеют **читать** источник и заполнять `trace_up` ссылкой на конкретный документ/тикет.
- Появляется автоматическая сверка «as-is из систем» vs «to-be из артефактов».

**Готово, когда:** ≥50% входа собирается из подключённых источников без копипаста.

---

## Горизонт 3 — Переписка и неструктурированные данные

**Цель:** извлекать намерения, боли и решения из живого общения.

| Источник (MCP) | Что извлекает |
|----------------|----------------|
| Gmail / почта | боли клиентов, договорённости, требования из переписки |
| Slack / Teams | обсуждения, решения, возражения стейкхолдеров |
| Транскрипты встреч / Calendar | принятые решения → кандидаты в ADR; задачи → требования |

- Скиллы **извлекают кандидатов** в артефакты (цель, требование, принцип, ADR) с пометкой `source: переписка` и низким `status: draft`.
- Человек подтверждает/отклоняет (human-in-the-loop) перед `approved`.
- Решения из встреч автоматически предлагаются как **ADR** в `it-architecture`.

**Готово, когда:** скилл предлагает ≥N валидных черновиков требований/ADR из переписки за период.

---

## Горизонт 4 — Замкнутая петля доработки продукта

**Цель:** скиллы используются не только для проектирования «с нуля», но и для **непрерывной доработки** живого продукта.

- **Drift-детект:** валидатор сравнивает артефакты с фактической телеметрией/инцидентами → находит расхождение «спроектировано vs реально работает».
- **Обратные триггеры:**
  - инцидент / рост Cost of Risk → пересмотр capability и требований;
  - фидбэк пользователей (поддержка, NPS) → кандидаты в цели Vision;
  - новый регуляторный акт → авто-проверка принципов (`constitution`) и затронутых ADR.
- Скиллы выдают **delta-предложения** (что изменить в Vision/CAP/архитектуре), а не полный документ заново.
- Интеграция с трекером: подтверждённая delta → автоматически создаётся эпик/задача (Jira/Linear MCP).

**Готово, когда:** изменение в продукте (инцидент/фидбэк/регулятор) автоматически порождает трассируемое предложение по правке артефактов.

---

## Горизонт 5 — Автономная continuous-architecture

**Цель:** цепочка работает как непрерывный процесс, человек — на approve и эскалациях.

- `orchestrator` по расписанию переснимает as-is из источников, прогоняет цепочку и валидатор, публикует diff.
- Авто-эскалация только при `principle-violation` или `fail` gate.
- Полная двунаправленная трассируемость: от строки регуляторного требования до ИТ-компонента и обратно.

**Готово, когда:** цепочка поддерживается в актуальном состоянии без ручного перезапуска, человек реагирует только на флаги.

---

## Сводная карта горизонтов

| Горизонт | Ключевое добавление | Источник входа | Степень автономности |
|----------|---------------------|----------------|----------------------|
| 0 | 4 базовых скилла | ручной | низкая |
| 1 | constitution + orchestrator | ручной | низкая+ |
| 2 | MCP к системам (доки, трекер, БД, CMDB) | системы | средняя |
| 3 | MCP к переписке (почта, чаты, встречи) | неструктур. | средняя+ |
| 4 | петля доработки (drift, инциденты, фидбэк) | продукт в проде | высокая |
| 5 | continuous-architecture | всё выше | автономная |

---

## Сквозные требования к развитию

- **Human-in-the-loop** на всех горизонтах с MCP: извлечённое из источников/переписки попадает как `draft`, повышается до `approved` только человеком.
- **Provenance:** у каждого элемента сохраняется `source` (откуда взят: документ/тикет/письмо/встреча).
- **Безопасность данных:** доступ к перепискам и внутренним системам — по политике доступа; PII/чувствительные данные не утекают в артефакты без маскирования.
- **Обратная совместимость handoff-контракта** между горизонтами.

## Что НЕ входит

- Реализация скиллов и MCP-коннекторов (создаётся отдельно, по отдельным ТЗ).
- Привязка к конкретной отрасли — базовая версия универсальна.
