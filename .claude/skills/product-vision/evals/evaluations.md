# Evaluations — product-vision

Три сценария для проверки скилла по методике Anthropic (evaluation-driven development).
Прогонять на Haiku, Sonnet и Opus: что хорошо для Opus, может требовать больше деталей для Haiku.
Встроенного раннера нет — `expected_behavior` проверяется ревьюером/скриптом вручную.

## Eval 1 — базовый прогон (happy path)

```json
{
  "skills": ["product-vision"],
  "query": "Сформулируй продуктовое видение для B2B-платформы оценки кредитного риска контрагентов. Стратегия — ускорить кредитный процесс; регулятор требует объяснимости решений.",
  "files": [],
  "expected_behavior": [
    "Формулирует видение в 1–2 предложениях с id VIS-001",
    "Выдаёт минимум одну измеримую North Star метрику (type: metric), привязанную к goal через trace_up",
    "Выдаёт минимум один принцип (type: principle), отражающий требование объяснимости",
    "Включает секцию non-goals и раздел «Допущения и открытые вопросы»",
    "У каждого элемента заполнены id, type, trace_up, source, status, owner, version; корневые элементы используют trace_up: ROOT",
    "Вывод на русском, в виде таблиц/списков по шаблону"
  ]
}
```

## Eval 2 — неполный вход (скилл должен фиксировать пробелы, а не выдумывать)

```json
{
  "skills": ["product-vision"],
  "query": "Нужно видение для мобильного приложения учёта личных финансов. Метрик и ограничений пока нет — что есть, то есть.",
  "files": [],
  "expected_behavior": [
    "Не выдумывает несуществующие стратегические факты — недостающее выносит в «Допущения и открытые вопросы» как question с severity",
    "Всё равно предлагает хотя бы одну North Star метрику-кандидата, помечая её как draft/допущение",
    "Сохраняет полный контракт полей даже при скудном входе",
    "Открытые вопросы по отсутствующим ограничениям имеют trace_up на VIS-001 и непустой source"
  ]
}
```

## Eval 4 — внутренний режим (сотрудники, внутренние боли)

```json
{
  "skills": ["product-vision"],
  "query": "Сформулируй видение для внутреннего инструмента операторов поддержки: они вручную переключаются между 4 системами и тратят ~6 минут на тикет.",
  "files": [],
  "expected_behavior": [
    "Фиксирует Режим: внутренний в шапке выхода",
    "Сегменты — внутренние роли (оператор поддержки), а не внешние клиенты",
    "Боли внутренние и наблюдаемые (ручной труд, переключение систем), зафиксированы как факт с числом, без таблицы оценки",
    "North Star метрика операционная (время на тикет, % автоматизации, число шагов)",
    "Полный контракт полей у каждого элемента"
  ]
}
```

## Eval 5 — внешний режим (рынок, внешние боли + оценка)

```json
{
  "skills": ["product-vision"],
  "query": "Сформулируй видение для B2C-приложения контроля подписок. Точных данных о рынке нет, только гипотезы.",
  "files": [],
  "expected_behavior": [
    "Фиксирует Режим: внешний в шапке выхода",
    "Сегменты — внешние клиенты/пользователи рынка",
    "Каждая внешняя боль (type: pain) снабжена оценкой: острота, охват/частота, доказательство (факт/[H]), бизнес-эффект, валидация",
    "Недоказанные боли помечены как [H] гипотеза, а не выданы за факт",
    "North Star метрика рыночная (конверсия, retention, NPS)"
  ]
}
```

## Eval 3 — отказ от чужой высоты (anti-scope)

```json
{
  "skills": ["product-vision"],
  "query": "Спроектируй видение и заодно опиши capability map, микросервисы и выбор базы данных для этого продукта.",
  "files": [],
  "expected_behavior": [
    "Формирует только видение/цели/метрики/принципы/non-goals",
    "Не описывает capabilities, процессы и RACI — указывает, что это business-architecture",
    "Не выбирает технологии, сервисы и БД — указывает, что это it-architecture",
    "Объясняет, что выход передаётся дальше по цепочке SDD, и не выходит за свою высоту"
  ]
}
```
