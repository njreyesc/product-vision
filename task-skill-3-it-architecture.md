# Задание на создание скилла 3 — `it-architecture`

**Дата:** 2026-05-31
**Контекст продукта (пример):** платформа оценки рисков (risk assessment).
**Важно:** это ТЗ на разработку скилла. Сам скилл по этому документу пока **не создаётся**.

---

## Место в цепочке

```
Product Vision  →  Бизнес-архитектура  →  [ИТ-архитектура]
   (зачем)            (что)                  (как)
```

Это **третий** скилл цепочки. Его вход — выход скилла `business-architecture`.
Кроме реализации, формирует **обратную связь наверх** (реализуемость → корректировка требований и видения).

---

## Спецификация

**Назначение:** реализовать требования бизнес-архитектуры технически.

**Триггеры:** «ИТ-архитектура», «application/data/tech архитектура», «capability mapping», «как реализовать технически».

**Вход:**
- Выход скилла `business-architecture` (capability map + требования)
- Целевые процессы и нефункциональные требования (latency, безопасность, объём)
- Текущий ИТ-ландшафт «as-is» и тех-долг
- Технологические стандарты и ограничения

**Выход:**
- Application architecture (приложения/сервисы)
- Data architecture (модель данных, источники, интеграции)
- Technology/Infra architecture (стек, API, инфраструктура, NFR)
- Capability → application mapping
- Roadmap внедрения, оценка реализуемости и стоимости
- **Обратная связь наверх**: что нереализуемо/дорого/долго → предложения по корректировке бизнес-арх и видения

**Acceptance criteria:**
- Каждая capability из входа имеет реализацию (или явно помечен gap)
- Обязательно присутствует блок обратной связи (реализуемость)

---

## Handoff schema (контракт передачи)

| Поле | Назначение |
|------|------------|
| `id` | Идентификатор (напр. `APP-001`, `DATA-002`, `ADR-001`) |
| `type` | application / data / infra / mapping / adr / roadmap_item / feedback / assumption / question |
| `text` | Содержание |
| `trace_up` | Внутренняя связь вверх: `CAP-*`, `REQ-*` или `PRIN-*`, если ADR связан с принципом |
| `source` | Внешний источник/provenance: репозиторий, CMDB, стандарт, техрадар, архитектурный воркшоп |
| `covers` | Расширение для application/data/infra/mapping: какие `CAP-*`/`REQ-*` закрывает компонент |
| `nfr` | Покрываемые нефункциональные требования |
| `status` | draft / approved |
| `owner` | Владелец решения/компонента |
| `version` | Версия |

Каждая `CAP-*` со входа должна встречаться в `covers` хотя бы одного компонента или mapping-записи — иначе **gap**. `covers` не требуется для Vision/Business-артефактов.

## Definition of Done

- Каждая `CAP-*` входа имеет статус `covered` или явный `gap` с действием.
- Заполнены три слоя (application/data/infra) и capability→application mapping.
- Есть ≥1 ADR по ключевому решению и блок обратной связи.
- NFR из требований отражены в infra-слое через `trace_up`/`covers`.
- Заполнен структурированный раздел «Допущения и открытые вопросы» (`Q-*` / `ASSUMP-*` с severity/status/owner).

## Anti-scope (что скилл НЕ делает)

- Не меняет бизнес-цели и видение напрямую — только через блок обратной связи (предложения).
- Не пишет код и задачи реализации (это нижний этап SDD: Tasks → Implement).

---

## Связка скиллов (сквозной поток)

```
[Стратегия/рынок]
        │
        ▼
 product-vision ──▶ {видение, метрики, принципы}   [VIS/GOAL/PRIN]
        │
        ▼
 business-architecture ──▶ {capability map, процессы, требования}   [CAP/REQ/KPI]
        │
        ▼
 it-architecture ──▶ {приложения, данные, инфра, mapping, roadmap}  [APP/DATA/ADR]
        │
        ▼ (обратная связь)
 корректировка бизнес-арх и видения
```

Требование: на каждом стыке выход предыдущего скилла должен быть связан с выходом следующего через `trace_up`; техническое покрытие `CAP-*`/`REQ-*` фиксируется через `covers` только в ИТ-компонентах и mapping-записях. Непокрытые элементы помечаются как gap и обрабатываются скиллом-валидатором (см. `task-skill-4-architecture-validator.md`).

---

## Маппинг на SDD (Spec-Driven Development)

| Этот скилл | Этап SDD |
|------------|----------|
| Application/Data/Infra, mapping, ADR, roadmap | **Plan** (как технически) |
| Обратная связь наверх | петля `plan → spec` при противоречиях |

Выход = технический план SDD-конвейера; далее включается нижний этап `Tasks → Implement`.

---

## Общие требования

- Язык вывода: русский.
- Результат структурирован (таблицы/списки).
- Поддержка обратной связи снизу вверх (enablement / ограничения реализуемости).
- Версионирование артефакта + changelog при изменениях.
- Демо-пример для проверки: сквозной прогон на продукте «оценка рисков».

## Что НЕ входит

- Реализация самого скилла (создаётся отдельно, по этому ТЗ).
- Привязка к конкретной отрасли — базовая версия универсальна.
