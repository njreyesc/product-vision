# Задание на создание скилла 2 — `business-architecture`

**Дата:** 2026-05-31
**Контекст продукта (пример):** платформа оценки рисков (risk assessment).
**Важно:** это ТЗ на разработку скилла. Сам скилл по этому документу пока **не создаётся**.

---

## Место в цепочке

```
Product Vision  →  [Бизнес-архитектура]  →  ИТ-архитектура
   (зачем)             (что)                  (как)
```

Это **второй** скилл цепочки. Его вход — выход скилла `product-vision`, его выход — вход для `it-architecture`.
Принцип: выход предыдущего этапа = вход следующего; предусмотрена обратная связь снизу вверх.

---

## Спецификация

**Назначение:** перевести видение в устройство бизнеса (capabilities, процессы, метрики).

**Триггеры:** «бизнес-архитектура», «capability map», «карта возможностей», «процессы to-be».

**Вход:**
- Выход скилла `product-vision` (видение, value proposition, метрики, принципы)
- Существующие процессы «as-is»
- Оргструктура, роли, регуляторные требования
- Бизнес-модель и финансовые ограничения

**Выход:**
- Карта бизнес-возможностей (capability map)
- Целевые процессы «to-be» / ценностные потоки
- Бизнес-требования к каждой capability (функциональные + нефункциональные)
- Метрики/KPI по процессам
- Модель ролей и ответственности (RACI)

**Acceptance criteria:**
- Каждая capability связана с целью/метрикой из видения (трассируемость вверх)
- Требования сформулированы измеримо (пригодны как вход для ИТ-архитектуры)

---

## Handoff schema (контракт передачи)

| Поле | Назначение |
|------|------------|
| `id` | Идентификатор (напр. `CAP-001`, `REQ-002`, `KPI-001`) |
| `type` | capability / process / requirement / kpi / role / raci / assumption / question |
| `text` | Содержание |
| `trace_up` | Внутренняя связь вверх: `id` из `product-vision` (`GOAL-*`, `MET-*`, `PRIN-*`, `SEG-*`) или родительская `CAP-*` для дочерних требований |
| `source` | Внешний источник/provenance: as-is процесс, оргструктура, регуляторика, бэклог, интервью |
| `priority` | MoSCoW: Must / Should / Could / Won't |
| `nfr` | Нефункциональные ограничения (если есть) |
| `status` | draft / approved |
| `owner` | Владелец (RACI: Accountable) |
| `version` | Версия |

Каждая capability обязана иметь `trace_up` на элемент Vision. Каждое требование обязано иметь `trace_up` на `CAP-*` или напрямую на `PRIN-*`, если требование реализует принцип. `source` не подменяет `trace_up`: он фиксирует происхождение данных.


## Definition of Done

- Каждая capability имеет `trace_up`, `priority` и хотя бы один KPI.
- Каждое требование измеримо, привязано к capability через `trace_up` и имеет `source`.
- Заполнены RACI и структурированный раздел «Допущения и открытые вопросы» (`Q-*` / `ASSUMP-*` с severity/status/owner).
- Принципы из видения (`PRIN-*`) отражены в требованиях.

## Anti-scope (что скилл НЕ делает)

- Не формулирует видение и стратегию (это `product-vision`).
- Не выбирает конкретные системы, стек и интеграции (это `it-architecture`).

---

## Маппинг на SDD (Spec-Driven Development)

| Этот скилл | Этап SDD |
|------------|----------|
| Capability map, процессы, требования, KPI | **Specify** (детализация «что» до измеримых требований) |

Выход = средняя часть спецификации: уточняет намерение из Vision до измеримых требований, готовых к технологическому планированию.

---

## Общие требования

- Язык вывода: русский.
- Результат структурирован (таблицы/списки), пригоден как вход следующего скилла.
- Версионирование артефакта + changelog при изменениях.
- Демо-пример для проверки: сквозной прогон на продукте «оценка рисков».

## Что НЕ входит

- Реализация самого скилла (создаётся отдельно, по этому ТЗ).
- Привязка к конкретной отрасли — базовая версия универсальна.
